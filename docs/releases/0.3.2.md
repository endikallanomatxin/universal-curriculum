# 0.3.2

## Main objective

Keep curriculum browsing and proposal editing responsive as the curriculum and
the number of concurrent contributors grow.

## Changes

- Separated lightweight curriculum structure reads from full unit content and
  loaded Markdown only when a unit document is opened.
- Made curriculum searches return bounded summaries from PostgreSQL instead of
  materializing every unit's content in application memory.
- Replaced the global curriculum advisory lock with shared projection locks and
  proposal-specific row locks, allowing different drafts to change concurrently.
- Kept rebase planning non-blocking and propagated request cancellation through
  its read-only database snapshot.
- Avoided graph reconstruction when a draft already targets the current
  curriculum proposal.
- Made curriculum modification content and historical diffs load one focused
  unit at a time, including proposal-created and retired units.
- Replaced eager dependency and recognition picker catalogs with debounced,
  bounded server-side searches that preserve proposal working-state semantics.
- Made acceptance apply only the accepted proposal to the materialized
  curriculum instead of replaying the complete publication history.
- Deferred stale-draft rebases until a draft is opened or modified and avoided
  calculating full rebase plans for every draft in proposal lists.
- Resolved MCP proposal-unit responses from focused unit history and immediate
  relationships instead of reconstructing the complete curriculum graph.
- Added trigram indexes for published unit name and content search.
- Bounded expensive graph-order optimization for large proposal overviews.
- Bounded the PostgreSQL connection pool and exposed its utilization through
  health response headers.
